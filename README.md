# Личный бюджет

Приложение для ручного учёта доходов и расходов, просмотра итогов месяца и контроля бюджетов по категориям.

## Возможности и экраны

| Экран | Адрес | Возможности |
| --- | --- | --- |
| Обзор | `/` | Выбор месяца, доходы, расходы, разница, расходы по категориям и последние операции |
| Операции | `/transactions` | Список записей, фильтры по месяцу, типу и категории, сброс фильтров |
| Новая операция | `/transactions/new` | Добавление дохода или расхода с суммой, категорией, датой и комментарием |
| Бюджеты | `/budgets` | Установка и изменение месячных лимитов, расходы, остаток и превышение по категориям |
| Настройки | `/settings` | Переключение светлой и тёмной темы |

Основные разделы доступны через общее меню. Неизвестный адрес открывает страницу с предложением вернуться к обзору. Интерфейс адаптируется к узкому экрану и поддерживает навигацию с клавиатуры.

## Пользовательские сценарии

1. Выбрать месяц в обзоре и оценить доходы, расходы и их разницу.
2. Найти операции по месяцу, типу и категории.
3. Добавить операцию: заполнить обязательные поля, исправить ошибки при необходимости и сохранить. Запись появится в списке, а итоги обзора и бюджетов пересчитаются.
4. Выбрать месяц и категорию в бюджетах, установить лимит и сравнить его с фактическими расходами. Повторное сохранение заменяет лимит только для выбранной категории и месяца.
5. Переключить тему в настройках. Выбор сохраняется после обновления страницы.

## Данные и ограничения

Frontend пока работает на демонстрационных данных независимо от backend. При запуске создаются шесть операций за текущий и предыдущий месяц и четыре лимита на текущий месяц. Backend на FastAPI запускается отдельно: подключён PostgreSQL, созданы модели и миграция таблиц, работает API категорий и операций. API бюджетов пока не реализован.

Операции и бюджеты frontend хранятся в памяти: переходы между страницами сохраняют изменения, обновление страницы возвращает демонстрационные данные. Данные, созданные через API, сохраняются в PostgreSQL и остаются после перезапуска backend. Тема хранится отдельно в браузере.

Валюта — рубли, категории frontend заданы заранее. Суммы хранятся в целых копейках. Форма принимает положительные суммы до 999 999 999,99 ₽ с точкой или запятой, проверяет дату, категорию и комментарий до 200 символов. Разница в обзоре — доходы минус расходы выбранного месяца, а не остаток на банковском счёте.

Регистрация, банковские интеграции, конвертация валют, редактирование и удаление операций через интерфейс пока не реализованы.

## Технологии

React, TypeScript, Vite, React Router, Material UI и Emotion. Для проверки логики используется встроенный тестовый модуль Node.js, для сценариев в браузере — Playwright.

Серверная часть: Python, FastAPI, Uvicorn, PostgreSQL, SQLAlchemy, драйвер Psycopg, Alembic для миграций и Pydantic Settings для конфигурации окружения.

Требуются Node.js 22.12+ и npm. В терминале из корня проекта:

## Запуск backend

Требуется Python 3.12+ и работающий PostgreSQL (проверено с PostgreSQL 18). При первой настройке выполните в PowerShell из корня проекта:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Если окружение уже существует, повторно создавать его не нужно. После изменения
`requirements.txt` повторите установку зависимостей. Существующий `.env` сохраняется.
Подготовьте базу и примените миграции по инструкции ниже, затем из папки `backend`:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Для последующих запусков достаточно этой команды и работающей службы PostgreSQL.
Активация окружения не требуется: команда явно использует Python из `.venv`.
Остановка сервера — Ctrl+C.

- `http://127.0.0.1:8000/api/health` — ответ `{"status":"ok"}` со статусом 200;
- `http://127.0.0.1:8000/api/health/db` — проверка подключения к PostgreSQL;
- `http://127.0.0.1:8000/docs` — интерактивная документация API;
- `http://127.0.0.1:8000/openapi.json` — схема API.

`/api/health` подтверждает работу приложения. `/api/health/db` выполняет `SELECT 1`:
при успешном подключении возвращает `{"status":"ok"}`, при ошибке БД — статус 503
и сообщение «База данных недоступна.». Эта проверка не проверяет наличие таблиц;
версию схемы показывает Alembic.
Frontend запускается отдельно в другом терминале из корня проекта.

Настройки читаются из `backend/.env` независимо от рабочей папки.
Переменные окружения имеют приоритет над `.env`.

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `FINANCE_APP_NAME` | `Personal Finance API` | Название в документации API |
| `FINANCE_DEBUG` | `false` | Режим отладки FastAPI |
| `FINANCE_DB_HOST` | `127.0.0.1` | Адрес PostgreSQL |
| `FINANCE_DB_PORT` | `5432` | Порт PostgreSQL |
| `FINANCE_DB_NAME` | `personal_finance` | База приложения |
| `FINANCE_DB_USER` | `finance_app` | Пользователь приложения |
| `FINANCE_DB_PASSWORD` | Пустая строка | Пароль пользователя приложения |

Без `.env` используются значения по умолчанию. Неизвестные параметры в этом
файле и некорректные значения вызывают ошибку конфигурации при запуске.
`.env` и `.venv` исключены из Git, в репозитории хранится `.env.example`.

### Подготовка PostgreSQL

Если база `personal_finance`, пользователь `finance_app` и настройки в `backend/.env`
уже созданы, переходите к миграциям. Повторно создавать их не нужно.

Для новой установки запустите службу PostgreSQL. pgAdmin и Docker не требуются:
команды можно выполнять в терминале VS Code. Подключитесь через `psql` (путь
ниже для стандартной установки PostgreSQL 18 на Windows):

```powershell
& 'C:\Program Files\PostgreSQL\18\bin\psql.exe' -h 127.0.0.1 -U postgres -d postgres -W
```

Введите пароль администратора локально. Внутри `psql` выполните:

```sql
CREATE ROLE finance_app LOGIN;
\password finance_app
CREATE DATABASE personal_finance OWNER finance_app;
\q
```

Команда `\password` запросит новый пароль пользователя приложения. Укажите его
в `FINANCE_DB_PASSWORD` файла `backend/.env`; остальные параметры должны соответствовать
созданной базе. Пароль администратора backend не нужен. Не добавляйте `.env` в Git.

### Создание и обновление таблиц

В PowerShell из папки `backend`:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic check
```

`upgrade head` применяет недостающие миграции; повторный запуск не пересоздаёт
таблицы. Текущая версия — `0001 (head)`. `check` проверяет соответствие схемы
SQLAlchemy фактической структуре БД. Таблицы создаются миграциями, запуск
Uvicorn не создаёт их автоматически.

### Модель данных

| Таблица | Поля | Связи и ограничения |
| --- | --- | --- |
| `categories` | `id` UUID, `name` до 80 символов, `type` | Тип `income` или `expense`; непустое имя; уникальная пара имени и типа |
| `transactions` | `id` UUID, `category_id` UUID, `amount_kopecks` BIGINT, `date` DATE, `comment` до 200 символов | Категория обязательна, тип операции определяется её категорией |
| `budgets` | `id` UUID, `category_id` UUID, `category_type`, `month` DATE, `limit_kopecks` BIGINT | Только расходные категории; один лимит на категорию и месяц |

В каждой таблице `id` — первичный ключ. Одна категория связана со многими
операциями и бюджетами. Внешние ключи не позволяют ссылаться на отсутствующую
категорию или удалить категорию, на которую ссылаются записи.

Суммы и лимиты — целые копейки от 1 до 99 999 999 999 включительно. Месяц
бюджета хранится датой первого числа. Служебное поле `budgets.category_type`
зафиксировано как `expense` и вместе с `category_id` образует внешний ключ
на `categories(id, type)`: база запрещает бюджет для доходной категории и
смену типа категории с существующим бюджетом. API также запрещает менять тип
категории с операциями, чтобы доходы не превращались в расходы при редактировании
справочника. Переименование такой категории разрешено.

SQLAlchemy описывает таблицы Python-классами и предоставляет сессии для работы
с данными. `get_engine()` создаёт общий пул подключений, `get_session()` выдаёт
сессию на запрос и закрывает её после завершения. Сохранение изменений требует
явного `commit()`; незавершённая транзакция при закрытии сессии откатывается.

## API категорий и операций

Все адреса начинаются с `/api`. Запросы и ответы используют JSON, идентификаторы — UUID.

| Метод | Категории | Операции | Результат |
| --- | --- | --- | --- |
| GET | `/categories` | `/transactions` | Список, статус 200 |
| GET | `/categories/{id}` | `/transactions/{id}` | Одна запись, статус 200 |
| POST | `/categories` | `/transactions` | Создание, статус 201 и сохранённая запись |
| PUT | `/categories/{id}` | `/transactions/{id}` | Полное обновление, статус 200 и сохранённая запись |
| DELETE | `/categories/{id}` | `/transactions/{id}` | Удаление, статус 204 без тела ответа |

В POST и PUT категории передаются `name` и `type` (`income` или `expense`).
Имя обрезается по краям, должно содержать от 1 до 80 символов. Пара имени и типа
уникальна; регистр учитывается. Категорию с операциями или бюджетами нельзя
удалить или сменить ей тип.

В POST и PUT операции обязательны `category_id`, `amount_kopecks` и `date`
в формате `YYYY-MM-DD`. `comment` необязателен, по умолчанию пустая строка,
максимум 200 символов. PUT заменяет все поля: пропущенный комментарий становится
пустым. Сумма — целое JSON-число от 1 до 99 999 999 999; строки, дроби и булевы
значения не принимаются. Лишние поля в теле запроса запрещены. Тип операции
определяется выбранной категорией; при обновлении можно выбрать другую категорию.

Списки возвращаются массивами. Параметры `limit` (по умолчанию 50, от 1 до 100)
и `offset` (по умолчанию 0, неотрицательный) задают страницу. Категории можно
фильтровать по `type`, сортировка — по имени и UUID. Операции фильтруются по
`category_id`, `type`, `date_from`, `date_to`; границы дат включаются. Сортировка
операций — от новых дат к старым, при равной дате по UUID. Пустая выборка — `[]`.

Ошибки возвращаются в поле `detail`:

- 404 — запись или категория операции не найдена;
- 409 — дубликат категории, попытка изменить связанную категорию или конфликт ограничений БД;
- 422 — неверные поля, UUID, сумма, дата, параметры списка или начало периода позже конца;
- 503 — ошибка подключения к БД.

При ошибках валидации `detail` содержит список проблем с указанием поля;
при бизнес-ошибках — сообщение. SQL и параметры подключения в ответ не попадают.
Изменения фиксируются через `commit()` только после проверок. При ошибке сессия
закрывается с откатом. Изменяемые записи блокируются на время транзакции,
чтобы проверки связей согласовывались с параллельными запросами API.

### Проверка через Swagger UI

Запустите backend и откройте `http://127.0.0.1:8000/docs`. Выберите маршрут,
нажмите **Try it out**, заполните тело и нажмите **Execute**.

1. Создайте категорию через `POST /api/categories`:

```json
{"name": "Продукты", "type": "expense"}
```

2. Скопируйте `id` из ответа и подставьте вместо `UUID_КАТЕГОРИИ` в `POST /api/transactions`:

```json
{
  "category_id": "UUID_КАТЕГОРИИ",
  "amount_kopecks": 125050,
  "date": "2026-09-21",
  "comment": "Покупка продуктов"
}
```

Это расход 1 250,50 ₽. GET `/api/transactions` покажет созданную операцию.
Проверьте PUT и DELETE, используя UUID из ответа. Перед удалением категории
удалите связанные операции. Ручные запросы сохраняют реальные данные в БД;
автоматические тесты откатывают свои изменения.

## Проверки и сборка

```bash
npm run lint
npm test
npm run build
npm run preview
```

`npm test` проверяет суммы, даты, категории, фильтры и месячные итоги. `npm run build` проверяет TypeScript и создаёт сборку в `dist`. `npm run preview` запускает локальный просмотр сборки.

Для браузерных проверок нужен установленный Microsoft Edge:

```bash
npm run test:e2e
```

Playwright запускает отдельный сервер на порту 4173, проверяет добавление операции и пересчёт итогов, бюджеты, фильтры, отмену, историю переходов, тему и страницы на ширине 1440 и 320 пикселей. Порт 4173 должен быть свободен. Скриншоты обновляются этим же запуском. Результаты временных проверок не включаются в Git.

Для размещения приложения на хостинге нужно настроить возврат `index.html` для клиентских маршрутов, например `/transactions`.

Проверки backend выполняются из папки `backend` после настройки БД и миграций:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Зависимости для тестирования включают HTTP-клиент `httpx2`, используемый
[TestClient](https://starlette.dev/testclient/). Их установка нужна при первой
настройке и после изменения `requirements-dev.txt`.

19 тестов проверяют структуру и ограничения PostgreSQL, CRUD через HTTP,
валидацию, фильтры, страницы списков, защиту связанных категорий, откат после
конфликта и ответ при недоступной БД. Запросы TestClient выполняются внутри
процесса: запускать Uvicorn для тестов не нужно. PostgreSQL должен работать.
Данные каждого теста находятся в отдельной транзакции и откатываются после проверки.

- `backend/app/api/` — маршруты API;
