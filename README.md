# Личный бюджет

Приложение для ручного учёта доходов и расходов, просмотра итогов месяца и контроля бюджетов по категориям.

## Возможности и экраны

| Экран | Адрес | Возможности |
| --- | --- | --- |
| Вход | `/login` | Вход по email и паролю, возврат к запрошенному разделу |
| Регистрация | `/register` | Создание учётной записи, проверка полей и подтверждения пароля |
| Обзор | `/` | Выбор месяца, доходы, расходы, разница, расходы по категориям и последние операции |
| Операции | `/transactions` | Список записей, фильтры по дате, типу и категории, редактирование и удаление с подтверждением |
| Новая операция | `/transactions/new` | Добавление дохода или расхода, создание своей категории |
| Редактирование операции | `/transactions/:id/edit` | Изменение типа, категории, суммы, даты и комментария с пересчётом итогов |
| Бюджеты | `/budgets` | Русский выбор месяца, установка, изменение и удаление лимитов, остаток и превышение |
| Категории | `/categories` | Создание, переименование, смена типа свободной категории и удаление |
| Настройки | `/settings` | Переключение светлой и тёмной темы |

Обзор, операции, бюджеты и категории доступны после входа через общее меню. Настройки, вход и регистрация публичны. Неизвестный адрес открывает страницу с предложением вернуться к обзору. Интерфейс адаптируется к узкому экрану и поддерживает навигацию с клавиатуры.

## Пользовательские сценарии

Сначала зарегистрироваться или войти. Новому пользователю автоматически создаются восемь категорий; операции и бюджеты изначально пусты. В меню отображается имя пользователя и кнопка выхода.

1. Выбрать месяц в обзоре и оценить доходы, расходы и их разницу.
2. Найти операции по дате, типу и категории.
3. Добавить операцию: заполнить обязательные поля, исправить ошибки при необходимости и сохранить. Запись появится в списке, а итоги обзора и бюджетов пересчитаются.
4. Выбрать месяц и категорию в бюджетах, установить лимит и сравнить его с фактическими расходами. Повторное сохранение заменяет лимит только для выбранной категории и месяца.
5. В списке операций нажать «Редактировать», изменить поля и сохранить. Для удаления выбрать «Удалить операцию» и подтвердить; отмена сохраняет запись. Итоги месяца и расходы в бюджетах пересчитываются.
6. Удалить месячный лимит кнопкой «Удалить лимит». Расходы, операции и лимиты других месяцев сохраняются.
7. На вкладке «Категории» создать, переименовать или удалить категорию. Новое имя сразу отображается в операциях и бюджетах. Тип категории со связанными записями изменить нельзя; удалить её можно только после удаления операций и лимитов.
8. Переключить тему в настройках. Выбор сохраняется после обновления страницы.

## Данные и ограничения

Frontend работает с FastAPI через `/api`. Данные хранятся в PostgreSQL и принадлежат конкретному пользователю. При обновлении страницы восстанавливается сессия и загружаются категории, операции и бюджеты его аккаунта. Созданные записи сохраняются после обновления страницы и перезапуска backend.

Файл `public/demo/finance.json` и деморепозиторий предыдущей лабораторной сохранены как тестовые данные. Рабочий интерфейс их не загружает. Тема хранится отдельно в браузере; access token хранится только в памяти, refresh token — в HttpOnly cookie.

Валюта — рубли, категории загружаются из API. Суммы хранятся в целых копейках. Форма принимает положительные суммы до 999 999 999,99 ₽ с точкой или запятой, проверяет дату, категорию и комментарий до 200 символов. Разница в обзоре — доходы минус расходы выбранного месяца, а не остаток на банковском счёте.

Банковские интеграции и конвертация валют пока не реализованы. Просмотр, создание, редактирование и удаление операций, лимитов и категорий доступны через интерфейс и защищённый API. Для бюджета редактируется лимит выбранной категории и месяца; перенос бюджета на другую категорию или месяц доступен через API.

## Технологии

React, TypeScript, Vite, React Router, Material UI и Emotion. Для проверки логики используется встроенный тестовый модуль Node.js, для сценариев в браузере — Playwright.

Серверная часть: Python, FastAPI, Uvicorn, PostgreSQL, SQLAlchemy, драйвер Psycopg, Alembic для миграций и Pydantic Settings для конфигурации окружения.

Для паролей используется Argon2id через pwdlib, для access token — PyJWT (HS256). Подход основан на [документации FastAPI](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/) и [рекомендациях OWASP по хранению паролей](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

## Запуск

Требуются Node.js 22.12+ и npm. В терминале из корня проекта:

```bash
npm ci
npm run dev
```

Сначала настройте и запустите backend по инструкции ниже, затем откройте адрес frontend из терминала, обычно `http://localhost:5173/`. Создайте аккаунт на странице регистрации. Остановка сервера — Ctrl+C. В PowerShell при блокировке `npm.ps1` используйте `npm.cmd` вместо `npm`.

Vite перенаправляет `/api` на `http://127.0.0.1:8000`; при другом адресе задайте `FINANCE_API_TARGET` перед запуском Vite. Этот прокси работает также для `npm run preview`. На хостинге нужен собственный прокси `/api` к backend и возврат `index.html` для клиентских маршрутов.

## Запуск backend

Требуется Python 3.12+ и работающий PostgreSQL (проверено с PostgreSQL 18). При первой настройке выполните в PowerShell из корня проекта:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
.\.venv\Scripts\python.exe -m scripts.configure_auth
```

Если окружение уже существует, повторно создавать его не нужно. После изменения
`requirements.txt` повторите установку зависимостей. Существующий `.env` сохраняется.
Подготовьте базу и примените миграции по инструкции ниже, затем из папки `backend`:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Для последующих запусков достаточно этой команды и работающей службы PostgreSQL.
Активация окружения не требуется: команда явно использует Python из `.venv`.
Остановка сервера — Ctrl+C.

- `http://127.0.0.1:8000/api/health` — ответ `{"status":"ok"}` со статусом 200;
- `http://127.0.0.1:8000/api/health/db` — проверка подключения к PostgreSQL;
- `http://127.0.0.1:8000/docs` — интерактивная документация API;
- `http://127.0.0.1:8000/openapi.json` — схема API.

`/api/health` подтверждает работу приложения. `/api/health/db` выполняет `SELECT 1`:
при успешном подключении возвращает `{"status":"ok"}`, при ошибке БД — статус 503
и сообщение «База данных недоступна.». Эта проверка не проверяет наличие таблиц;
версию схемы показывает Alembic.
Frontend запускается отдельно в другом терминале из корня проекта.

Настройки читаются из `backend/.env` независимо от рабочей папки.
Переменные окружения имеют приоритет над `.env`.

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `FINANCE_APP_NAME` | `Personal Finance API` | Название в документации API |
| `FINANCE_DEBUG` | `false` | Режим отладки FastAPI |
| `FINANCE_DB_HOST` | `127.0.0.1` | Адрес PostgreSQL |
| `FINANCE_DB_PORT` | `5432` | Порт PostgreSQL |
| `FINANCE_DB_NAME` | `personal_finance` | База приложения |
| `FINANCE_DB_USER` | `finance_app` | Пользователь приложения |
| `FINANCE_DB_PASSWORD` | Пустая строка | Пароль пользователя приложения |
| `FINANCE_DB_SCHEMA` | `public` | Схема PostgreSQL; браузерные тесты используют временную схему |
| `FINANCE_JWT_SECRET` | Обязателен | Секрет подписи JWT, минимум 32 байта; генерируется `scripts.configure_auth` |
| `FINANCE_ACCESS_TOKEN_SECONDS` | `900` | Access token: 15 минут |
| `FINANCE_REFRESH_TOKEN_SECONDS` | `604800` | Refresh-сессия: 7 дней с момента входа |
| `FINANCE_COOKIE_SECURE` | `false` | Для локального HTTP; при HTTPS установите `true` |

`scripts.configure_auth` добавляет случайный секрет в `.env`, сохраняя существующий секрет и настройки БД. Неизвестные параметры в этом файле, отсутствующий JWT-секрет и некорректные значения вызывают ошибку конфигурации при запуске.
`.env` и `.venv` исключены из Git, в репозитории хранится `.env.example`.

### Подготовка PostgreSQL

Если база `personal_finance`, пользователь `finance_app` и настройки в `backend/.env`
уже созданы, переходите к миграциям. Повторно создавать их не нужно.

Для новой установки запустите службу PostgreSQL. pgAdmin и Docker не требуются:
команды можно выполнять в терминале VS Code. Подключитесь через `psql` (путь
ниже для стандартной установки PostgreSQL 18 на Windows):

```powershell
& 'C:\Program Files\PostgreSQL\18\bin\psql.exe' -h 127.0.0.1 -U postgres -d postgres -W
```

Введите пароль администратора локально. Внутри `psql` выполните:

```sql
CREATE ROLE finance_app LOGIN;
\password finance_app
CREATE DATABASE personal_finance OWNER finance_app;
\q
```

Команда `\password` запросит новый пароль пользователя приложения. Укажите его
в `FINANCE_DB_PASSWORD` файла `backend/.env`; остальные параметры должны соответствовать
созданной базе. Пароль администратора backend не нужен. Не добавляйте `.env` в Git.

### Создание и обновление таблиц

В PowerShell из папки `backend`:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic check
```

`upgrade head` применяет недостающие миграции; повторный запуск не пересоздаёт
таблицы. Текущая версия — `0002 (head)`. `check` проверяет соответствие схемы
SQLAlchemy фактической структуре БД. Таблицы создаются миграциями, запуск
Uvicorn не создаёт их автоматически.

### Модель данных

| Таблица | Поля | Связи и ограничения |
| --- | --- | --- |
| `users` | `id` UUID, `email`, `name`, `password_hash`, `is_active`, `created_at` | Email нормализован и уникален; пароль хранится как Argon2id-хеш |
| `refresh_sessions` | `id` UUID, `user_id`, `token_hash`, `expires_at`, `revoked_at`, `created_at` | Связь с пользователем; уникальный SHA-256-хеш случайного refresh token |
| `categories` | `id` UUID, `owner_id` UUID, `name` до 80 символов, `type` | Владелец — пользователь; тип `income` или `expense`; уникальность владельца, имени и типа |
| `transactions` | `id` UUID, `category_id` UUID, `amount_kopecks` BIGINT, `date` DATE, `comment` до 200 символов | Категория обязательна, тип операции определяется её категорией |
| `budgets` | `id` UUID, `category_id` UUID, `category_type`, `month` DATE, `limit_kopecks` BIGINT | Только расходные категории; один лимит на категорию и месяц |

В каждой таблице `id` — первичный ключ. Одна категория связана со многими
операциями и бюджетами. Внешние ключи не позволяют ссылаться на отсутствующую
категорию или удалить категорию, на которую ссылаются записи.

Суммы и лимиты — целые копейки от 1 до 99 999 999 999 включительно. Месяц
бюджета хранится датой первого числа. Служебное поле `budgets.category_type`
зафиксировано как `expense` и вместе с `category_id` образует внешний ключ
на `categories(id, type)`: база запрещает бюджет для доходной категории и
смену типа категории с существующим бюджетом. API также запрещает менять тип
категории с операциями, чтобы доходы не превращались в расходы при редактировании
справочника. Переименование такой категории разрешено.

Операции и бюджеты принадлежат пользователю через категорию. Миграция `0002` сохраняет старые финансовые записи под отключённым архивным пользователем: новые аккаунты их не получают. Пароль архивного аккаунта не позволяет вход.

SQLAlchemy описывает таблицы Python-классами и предоставляет сессии для работы
с данными. `get_engine()` создаёт общий пул подключений, `get_session()` выдаёт
сессию на запрос и закрывает её после завершения. Сохранение изменений требует
явного `commit()`; незавершённая транзакция при закрытии сессии откатывается.

## API категорий, операций и бюджетов

Все адреса начинаются с `/api`. Запросы и ответы используют JSON, идентификаторы — UUID.

Все маршруты категорий, операций и бюджетов требуют `Authorization: Bearer <access_token>`. Списки содержат только собственные записи. Чтение, изменение или удаление чужого UUID и привязка чужой категории возвращают 404; владелец определяется сервером.

| Метод | Категории | Операции | Бюджеты | Результат |
| --- | --- | --- | --- | --- |
| GET | `/categories` | `/transactions` | `/budgets` | Список, статус 200 |
| GET | `/categories/{id}` | `/transactions/{id}` | `/budgets/{id}` | Одна запись, статус 200 |
| POST | `/categories` | `/transactions` | `/budgets` | Создание, статус 201 и сохранённая запись |
| PUT | `/categories/{id}` | `/transactions/{id}` | `/budgets/{id}` | Полное обновление, статус 200 и сохранённая запись |
| DELETE | `/categories/{id}` | `/transactions/{id}` | `/budgets/{id}` | Удаление, статус 204 без тела ответа |

В POST и PUT категории передаются `name` и `type` (`income` или `expense`).
Имя обрезается по краям, должно содержать от 1 до 80 символов. Пара имени и типа
уникальна в рамках аккаунта; регистр учитывается. Категорию с операциями или бюджетами нельзя
удалить или сменить ей тип.

В POST и PUT операции обязательны `category_id`, `amount_kopecks` и `date`
в формате `YYYY-MM-DD`. `comment` необязателен, по умолчанию пустая строка,
максимум 200 символов. PUT заменяет все поля: пропущенный комментарий становится
пустым. Сумма — целое JSON-число от 1 до 99 999 999 999; строки, дроби и булевы
значения не принимаются. Лишние поля в теле запроса запрещены. Тип операции
определяется выбранной категорией; при обновлении можно выбрать другую категорию.

В POST и PUT бюджета обязательны `category_id`, `month` и `limit_kopecks`.
Категория должна иметь тип `expense`. Месяц передаётся датой первого числа,
например `2026-09-01`; другие дни отклоняются, автоматического округления нет.
Лимит — целое JSON-число от 1 до 99 999 999 999 копеек, без строк, дробей и булевых
значений. `category_type` — внутреннее поле БД: его не нужно передавать, в ответе
его тоже нет. Лишние поля запрещены.

Для одной категории в одном месяце допускается один бюджет. Повторный POST
возвращает 409 и сохраняет прежний лимит; для изменения используйте PUT с UUID
бюджета. PUT позволяет изменить лимит, месяц и расходную категорию, но требует
все три поля и проверяет уникальность нового сочетания категории и месяца.
Удаление бюджета удаляет только лимит: категория и операции сохраняются.

Списки возвращаются массивами. Параметры `limit` (по умолчанию 50, от 1 до 100)
и `offset` (по умолчанию 0, неотрицательный) задают страницу. Категории можно
фильтровать по `type`, сортировка — по имени и UUID. Операции фильтруются по
`category_id`, `type`, `date_from`, `date_to`; границы дат включаются. Сортировка
операций — от новых дат к старым, при равной дате по UUID. Пустая выборка — `[]`.

Бюджеты поддерживают те же `limit` и `offset`, а также фильтры `category_id`
и `month` (дата первого числа месяца). Сортировка — от новых месяцев к старым,
при равном месяце по UUID. Пример: `/api/budgets?month=2026-09-01&limit=20`.

Ошибки возвращаются в поле `detail`:

- 404 — запись или указанная категория не найдена;
- 401 — отсутствующий, недействительный или истёкший access token, отозванная сессия;
- 409 — дубликат категории или бюджета, попытка удалить связанную категорию или сменить её тип, конфликт ограничений БД;
- 422 — неверные поля, UUID, сумма, дата, месяц бюджета, доходная категория бюджета, параметры списка или начало периода позже конца;
- 503 — ошибка подключения к БД.

При ошибках валидации `detail` содержит список проблем с указанием поля;
при бизнес-ошибках — сообщение. SQL и параметры подключения в ответ не попадают.
Изменения фиксируются через `commit()` только после проверок. При ошибке сессия
закрывается с откатом. Изменяемые записи блокируются на время транзакции,
чтобы проверки связей согласовывались с параллельными запросами API.

### Проверка через Swagger UI

Запустите backend и откройте `http://127.0.0.1:8000/docs`. Выберите маршрут,
нажмите **Try it out**, заполните тело и нажмите **Execute**. Сначала вызовите `POST /api/auth/register` с `name`, `email`, `password` или `/api/auth/login` с `email`, `password`. Скопируйте `access_token` из ответа и вставьте его в **Authorize** (без слова Bearer). Начальные категории уже созданы; для проверки ниже используйте новое имя категории.

1. Создайте категорию через `POST /api/categories`:

```json
{"name": "Продукты для проверки", "type": "expense"}
```

2. Скопируйте `id` из ответа и подставьте вместо `UUID_КАТЕГОРИИ` в `POST /api/transactions`:

```json
{
  "category_id": "UUID_КАТЕГОРИИ",
  "amount_kopecks": 125050,
  "date": "2026-09-21",
  "comment": "Покупка продуктов"
}
```

Это расход 1 250,50 ₽. GET `/api/transactions` покажет созданную операцию.
Проверьте PUT и DELETE, используя UUID из ответа.

3. Для той же расходной категории создайте лимит 5 000 ₽ через `POST /api/budgets`:

```json
{
  "category_id": "UUID_КАТЕГОРИИ",
  "month": "2026-09-01",
  "limit_kopecks": 500000
}
```

Проверьте GET `/api/budgets?month=2026-09-01`. Для изменения лимита отправьте
все три поля в PUT `/api/budgets/{budget_id}`, подставив UUID бюджета из ответа.
Повторный POST той же категории и месяца должен вернуть 409, дата `2026-09-02`
или доходная категория — 422. DELETE `/api/budgets/{budget_id}` удалит лимит.

Перед удалением категории удалите связанные операции и бюджеты.
Ручные запросы сохраняют реальные данные в БД;
интеграционные тесты откатывают свои изменения, а проверка с перезапуском сервера
удаляет созданные ею записи после завершения.

## Лабораторная №3: архитектура frontend и динамический интерфейс

Этот раздел описывает предыдущий этап. В лабораторной №4 деморепозиторий заменён API-репозиторием, но структура модулей, проверки форм и состояния интерфейса сохранены. Текущий запуск требует backend и входа в аккаунт; актуальный сценарий описан в [проверке лабораторной №4](docs/lab4-check.md).

Выбрана упрощённая структура Feature-Sliced Design: `app → pages → features → entities → shared`. Верхние слои могут использовать нижние; общие компоненты не знают о сущностях, а сущности не импортируют страницы и пользовательские действия. Контекст и `useFinance` лежат в `entities`, а приложение подключает провайдер. Направление импортов проверяется автоматическим тестом. Финансовые сущности объединены в один модуль `finance`, поскольку операции и бюджеты используют одни категории и один набор данных. Полный FSD и отдельный слой widgets для этого размера проекта не требуются.

Страницы задают компоновку и локальное состояние выбора месяца/фильтров. Features содержат формы, клиентскую валидацию и реакцию на действия пользователя. Entities описывает типы операций и бюджетов, вычисляет итоги и работает с репозиторием данных. Shared содержит независимые компоненты состояний и утилиты. Формы не выполняют запросы сами: типизированные асинхронные обработчики передаются через свойства.

`FinanceProvider` загружает демоданные один раз на запуск приложения и предоставляет общее состояние через React Context. `AsyncState<FinanceData>` — объединение трёх состояний: `loading`, `error` и `ready`; данные доступны только в `ready`. Запросы отменяются при размонтировании и повторной загрузке, отменённый запрос не заменяет свежий результат. Ошибка HTTP, сети, JSON или структуры данных показывает понятное сообщение. Кнопка «Повторить загрузку» запускает запрос снова. Настройки и навигация доступны даже при ошибке данных.

Контракт `FinanceRepository` включает загрузку, добавление операции и сохранение бюджета. `DemoFinanceRepository` загружает JSON через `fetch`, проверяет его структуру и хранит изменения в памяти. Загрузка и сохранение имеют небольшую демонстрационную задержку 250 мс, чтобы были видны переходы состояния. Повторное открытие экрана не загружает исходные данные заново и не сбрасывает изменения. Перезагрузка браузера возвращает исходный JSON. Файл входит в сборку Vite; FastAPI и PostgreSQL для демонстрации лабораторной №3 не нужны.

Обе формы проверяют поля до сохранения, подписывают ошибки под соответствующими полями и переводят фокус на первое некорректное поле. Ошибки исправляются по мере ввода после первой отправки. Смена типа операции сбрасывает категорию. На время сохранения поля и кнопка блокируются, индикатор показывает выполнение; дополнительная защита в общем обработчике не допускает повторной отправки. При ошибке сохранения введённые данные остаются в форме. Новая операция появляется в списке и пересчитывает обзор и расходы бюджетов; сохранение лимита показывает подтверждение и обновляет только выбранную категорию и месяц.

Переход страницы длится 180 мс и использует появление со смещением на 8 px. Сообщения форм раскрываются через Material UI Collapse, индикаторы бюджетов плавно реагируют на изменение расходов. При `prefers-reduced-motion: reduce` CSS отключает анимацию страниц и сокращает переходы компонентов. При переходах фокус переносится на основное содержимое, страница прокручивается вверх; сохранены ссылки, история браузера, прямые адреса и экран неизвестного маршрута.

## Лабораторная №4: аутентификация и авторизация

| Метод и адрес | Назначение | Результат |
| --- | --- | --- |
| `POST /api/auth/register` | `name`, `email`, `password` (8–128 символов) | 201: пользователь и токены сессии |
| `POST /api/auth/login` | `email`, `password` | 200: пользователь и токены; неверные данные — 401 |
| `POST /api/auth/refresh` | Refresh из cookie | 200: новый access; недействительный, истёкший или отозванный refresh — 401 |
| `GET /api/auth/me` | Access в Bearer | 200: `id`, `email`, `name`; без доступа — 401 |
| `POST /api/auth/logout` | Cookie и при наличии Bearer | 204: отзыв текущей сессии и удаление cookie |

JSON ответа входа, регистрации и refresh содержит `access_token`, `token_type`, `expires_in`, `refresh_expires_in`, `user`. JWT проверяется по подписи, алгоритму, issuer, audience, времени истечения, пользователю и сессии. По умолчанию access действует 15 минут, refresh-сессия — 7 дней. При обновлении случайный refresh token заменяется новым, прежний больше не принимается; абсолютный срок сессии не продлевается.

Refresh передаётся в cookie `finance_refresh` с `HttpOnly`, `SameSite=Lax`, `Path=/api/auth`. БД содержит только его SHA-256-хеш. Пароли сохраняются только как Argon2id-хеши; ответы пользователя и ошибки валидации не возвращают пароль или его хеш. Для запросов изменения auth-состояния проверяется Origin. Публичны health, документация, регистрация и вход; refresh требует действующий cookie, финансовый API — действующий Bearer.

После перезагрузки frontend получает access через refresh и текущего пользователя через `/me`. При 401 клиент выполняет одно общее обновление для параллельных запросов и повторяет их один раз. Отклонённый refresh завершает сессию; сетевая ошибка позволяет повторить попытку. После подтверждённого выхода сбрасываются пользователь, access и финансовые данные. Сервер отзывает сессию, поэтому её refresh и уже выданные access больше не действуют. Другие сессии пользователя сохраняются.

Добавлены страницы входа и регистрации, имя и выход в меню; обновлены скриншоты. Результаты проверок и шаги для сдачи: [Проверка лабораторной №4](docs/lab4-check.md). По указанию пользователя изменения оставлены без коммита.


## Лабораторная №5: интеграция frontend и backend

Рабочие экраны используют FastAPI и PostgreSQL. Добавлены редактирование и удаление операций, удаление месячных лимитов и вкладка «Категории» с полным CRUD. Интерфейс применяет успешные ответы API и пересчитывает зависимые данные; ошибки не удаляют записи и не сбрасывают введённые поля. Удаление требует подтверждения. Права владельца проверяет сервер; чужая или удалённая операция по прямому адресу недоступна.

Инструкция запуска выше проверена с реальной БД. `npm.cmd run test:e2e` самостоятельно запускает frontend и API на свободных локальных портах и мигрирует временную схему PostgreSQL. Секрет и параметры БД читаются из локального `backend/.env`; браузерные тесты используют отдельные аккаунты, access на 2 секунды и удаляют тестовую схему после завершения. Серверы останавливаются автоматически, в том числе на Windows. Для запуска нужен установленный Microsoft Edge и зависимости `backend/requirements-dev.txt`.
