# Проверка лабораторной №4

## Соответствие заданию

| Пункт | Реализация | Проверка |
| --- | --- | --- |
| 1. Регистрация и вход, стойкие хеши | `/auth/register`, `/auth/login`; Argon2id через pwdlib; нормализация email; формы React с валидацией | Регистрация, повтор email, неверный пароль, хеш в БД |
| 2. Access и refresh с ограниченным сроком | JWT HS256 на 15 минут, случайный refresh на 7 дней, HttpOnly cookie, в БД SHA-256-хеш | Подпись и срок JWT, атрибуты cookie, отсутствие токенов в localStorage |
| 3. Обновление access | `/auth/refresh`; проверка сессии и пользователя, ротация refresh без продления срока | Корректный refresh принят; старый, отсутствующий, истёкший и отозванный отклонены |
| 4. Текущий пользователь и права | `/auth/me`; Bearer для финансового API; выборки по владельцу категории | Анонимные запросы 401; чужие UUID и категории 404; списки изолированы |
| 5. Выход | `/auth/logout`; отзыв текущей сессии, удаление cookie; сброс контекстов frontend | После выхода refresh и прежний access отклонены; другой сеанс продолжает работать |

## Запуск

Установка PostgreSQL, `.venv` и зависимостей описана в [README](../README.md). Для уже настроенного проекта в первом терминале из корня:

```powershell
cd backend
.\.venv\Scripts\python.exe -m scripts.configure_auth
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Во втором терминале из корня:

```powershell
npm.cmd run dev
```

Откройте `http://localhost:5173`. Если зависимости уже установлены, переустановка не нужна. После изменения `backend/requirements.txt` выполните установку заново. JWT-секрет генерируется локально в игнорируемом `.env`, пароль БД сохраняется. Миграция `0002` добавляет пользователей и сессии; прежние записи сохраняются у отключённого архивного аккаунта.

## Демонстрация в браузере

1. Выйдите из приложения, если уже авторизованы. Откройте напрямую `/budgets`: появится вход. Перейдите к регистрации, отправьте пустую форму, проверьте ошибки. Укажите имя, новый email, пароль от 8 символов и подтверждение. После регистрации откроются бюджеты — исходный запрошенный раздел.
2. У нового пользователя нет операций и лимитов, но есть категории. Добавьте расход и месячный бюджет. Проверьте пересчёт обзора и бюджета, затем обновите страницу: данные сохраняются в PostgreSQL.
3. Нажмите «Выйти». Имя и финансовые данные исчезнут, приватный адрес снова приведёт ко входу. Обновление страницы не возвращает пользователя. Проверьте неверный пароль и затем успешный вход: собственные записи восстановятся.
4. Зарегистрируйте второй аккаунт в другом профиле браузера или приватном окне. Его списки пусты; данные первого пользователя ему недоступны.
5. В DevTools → Application → Cookies у `finance_refresh` установлены HttpOnly и SameSite=Lax, путь `/api/auth`. Refresh не виден в `document.cookie`; localStorage содержит настройку темы, но не токены. В Network финансовые запросы используют Bearer.
6. По умолчанию access действует 15 минут. Для быстрой ручной демонстрации задайте перед запуском backend `$env:FINANCE_ACCESS_TOKEN_SECONDS='5'`, войдите заново, подождите больше 5 секунд и нажмите «Обновить данные» в операциях. В Network появится один `POST /api/auth/refresh`, затем успешные повторные запросы. После демонстрации остановите сервер и выполните `Remove-Item Env:FINANCE_ACCESS_TOKEN_SECONDS`, затем запустите обычный сервер.

## API и права доступа

Откройте `http://127.0.0.1:8000/docs`. Без Authorize финансовые маршруты и `/api/auth/me` возвращают 401; `/api/health` и документация доступны.

Вызовите `POST /api/auth/register`:

```json
{"name":"Проверка","email":"lab4-check@example.com","password":"TestPassword123"}
```

Повтор email возвращает 409, некорректные поля — 422. Для существующего аккаунта используйте `/auth/login`. Вставьте `access_token` в Authorize без префикса Bearer. `/auth/me` вернёт только `id`, `email`, `name`.

Регистрация, вход и refresh устанавливают cookie автоматически в браузере Swagger. `/auth/refresh` заменяет refresh token, сохраняя абсолютную дату окончания сессии. Сохранённый старый cookie после обновления отклоняется с 401. Несуществующий токен и истёкшая сессия также дают 401. Проверки истёкших и отозванных refresh воспроизводятся автоматическими тестами без изменения рабочих записей.

Создайте операцию под первым аккаунтом, скопируйте её UUID и UUID категории. Авторизуйтесь вторым аккаунтом: GET, PUT и DELETE этой операции возвращают 404. POST операции с чужой категорией тоже возвращает 404. Аналогичные проверки реализованы для категорий и бюджетов.

Вызовите `/auth/logout`, затем `/auth/refresh`: ожидаются 204 и 401. Повторите `/auth/me` со старым access: 401, даже если его срок ещё не истёк. Выход завершает только текущую сессию.
